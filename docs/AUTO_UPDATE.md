# ClassMate APK updates through GitHub Releases

ClassMate reads `update.json` from the latest **published** release in the public [`shuaibuddowla/ClassMate`](https://github.com/shuaibuddowla/ClassMate) repository. The same release contains a versioned signed APK. GitHub hosts both over HTTPS; no Cloudflare bucket, domain, or client-side publishing token is needed. The release script creates a draft, uploads the APK first and metadata last, verifies the assets, then publishes the release.

The app compares numeric `versionCode`, downloads into private storage, verifies size and SHA-256, checks the APK package, version and installed signing identity, and commits an Android `PackageInstaller` session. Android decides whether user confirmation is required. Authentication and app data are not cleared by an in-place update.

## Signing identity and initial install

The first production APK and **every update** must use the same production signing identity. The local ignored `keystore.properties` records the path to `classmatev2_key.jks`, alias `key0`, and its public certificate fingerprint. Passwords are not stored there. To build a signed release from Gradle, set `CLASSMATE_STORE_PASSWORD` and `CLASSMATE_KEY_PASSWORD` in the current PowerShell session or use Android Studio's signed APK wizard. Never post or commit passwords or the `.jks` file. Keep encrypted backups of the keystore and passwords.

The earlier USB-installed APK is debug signed. Android cannot install a `key0`-signed release on top of that debug build. Plan a one-time uninstall/reinstall for that phone after verifying any local-only data is backed up. Subsequent `key0`-signed releases can update in place.

ClassMate 1.1.6 (version code 7) is the published GitHub update baseline. For the next release, use a higher version code and a new version name, then build a fresh APK from that source with the same `key0` signing identity. Never reuse an old APK or published version tag.

## Source URL

Production builds default to:

```text
https://github.com/shuaibuddowla/ClassMate/releases/latest/download/update.json
```

The Gradle `UPDATE_BASE_URL` property can override the default. Staging builds do not consume production releases. The metadata must point to a versioned APK URL in the same repository, such as:

```text
https://github.com/shuaibuddowla/ClassMate/releases/download/v1.1.6/classmate-1.1.6.apk
```

Only HTTPS GitHub release URLs matching the configured repository and metadata version are accepted. Release-asset CDN redirects must also stay HTTPS. The APK still needs the trusted signing certificate even when its URL and hash match.

## Publish

1. Commit and push the source being released. Increment both `versionCode` and `versionName` in `app/build.gradle.kts` for each subsequent release.
2. Build an APK signed with `key0`. Set the two signing-password environment variables if using `-Build`; alternatively, pass a signed APK generated by Android Studio with `-ApkPath`. Keep the passwords out of chat and Git.
3. Validate the APK without uploading:

   ```powershell
   .\scripts\publish-classmate-github-update.ps1 -ApkPath .\app\build\outputs\apk\release\app-release.apk -ValidateOnly
   ```

4. Publish the first baseline or a later update:

   ```powershell
   .\scripts\publish-classmate-github-update.ps1 -ApkPath .\app\build\outputs\apk\release\app-release.apk -ReleaseNotes 'Bug fixes','Performance improvements'
   ```

   The script requires GitHub CLI (`gh`) authentication, checks package/version/certificate/hash, refuses an existing tag or equal/older published version code, creates a draft `v<versionName>` release, uploads `classmate-<versionName>.apk`, uploads `update.json`, verifies asset sizes and the available GitHub digest, then publishes it as latest. A failure after draft creation leaves the draft unpublished for inspection. `-Mandatory -MinSupportedVersionCode <code>` marks a version as required.

Do not publish a release built from stale or uncommitted code. Do not replace an already published APK or tag. Keep release assets immutable when available.

If Android Studio puts the signed APK in `release/app-release.apk`, pass that path to both commands instead. For example, the release after 1.1.6 could be `versionCode = 8` and `versionName = "1.1.7"`; use a distinct version name if that Git tag already exists. The script generates and uploads `update.json` automatically.

Example `update.json`:

```json
{
  "versionCode": 7,
  "versionName": "1.1.6",
  "minSupportedVersionCode": 6,
  "apkUrl": "https://github.com/shuaibuddowla/ClassMate/releases/download/v1.1.6/classmate-1.1.6.apk",
  "apkSize": 28439521,
  "sha256": "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa",
  "mandatory": false,
  "releaseDate": "2026-10-02T00:00:00Z",
  "releaseNotes": ["Improvements and bug fixes"]
}
```

## Client behavior

- WorkManager checks about every six hours. A foreground check is queued when at least one hour has passed. Automatic updates and Wi-Fi-only downloads default on and can be changed in Profile. Manual Check for Updates uses the same repository and verifier.
- Downloads are streamed to private storage. Interrupted temp files are removed. Only the current candidate remains. Size, hash, package, version, and signing failures block installation and delete the candidate.
- On API 31+, ClassMate requests `USER_ACTION_NOT_REQUIRED`; Android may still return `STATUS_PENDING_USER_ACTION`. ClassMate then opens the official confirmation UI when visible or provides a notification. Older Android versions use the official installer confirmation flow.
- If Android requires Install unknown apps authorization, ClassMate explains it and opens the package-specific settings screen. Android 13+ notification permission may affect background prompts.
- A mandatory release or an installed code below `minSupportedVersionCode` shows a blocking retry prompt after a valid APK has been verified. Use this only after real-device testing.

## Test v1 → v2

1. Build v1 and v2 with the same `key0` signing identity; v2 must have a higher `versionCode`. Both must include the GitHub update source. Install v1 on a test device.
2. Publish v1 as the baseline release, then publish v2 with its signed APK and metadata. On v1, open Profile → Check for Updates or wait for WorkManager.
3. Confirm that the APK is downloaded and verified; Android either installs it without interaction or shows its official installer. Verify v2 opens with the prior account and app data.
4. In an isolated test repository/build, exercise no network, metered Wi-Fi-only policy, malformed metadata, wrong hash/package/version/signer, permission denial, user cancellation, and reboot. A debug-signed APK cannot update a `key0` install.

## Disable a bad release

Mark the release as not latest or unpublish it so `/releases/latest` returns the previous release. An already installed newer APK cannot be downgraded by this updater. Publish a corrected APK with a **higher** version code and the same signing identity. If a mandatory release is bad, restore a safe latest release promptly and verify the link from an external network.
