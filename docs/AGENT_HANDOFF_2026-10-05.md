## 3. Accounts, identity, roles and onboarding

- Supabase Auth user UUID is the primary identity of `classmate.profiles`.
- Google university sign-in is enforced server-side. The intended email domain is **`@mbstu.ac.bd`**.
- Auth hook `classmate.before_user_created` and profile initialization verify provider/domain/confirmation. A modified client must not bypass these checks.
- Owner/admin authority comes from the owner allowlist. Teachers use an active allowlist and actual course assignments. CR is an active, expiring assignment on a student profile, not a freely selected role.
- Students are batch-scoped. Teachers are assignment-scoped. Owners can select/manage broader scopes. Server policies remain authoritative.
- Profile initialization/onboarding APIs include `create_or_initialize_profile`, `complete_student_onboarding`, owner approval/rejection, `assign_cr` and `revoke_cr`.

Existing numeric end-year fields remain compatible; do not convert every database integer to a string without checking models. Native `ClassMateAcademicSession` and web `academic-session.ts` format it.
- Departments with no parsing rule use pending manual approval rather than inventing a batch.
- New-account onboarding has three steps: **We found your account → Complete your profile → Enable notifications**.
- Profile completion asks mobile number, home town, blood group, and current mess/flat (optional). Continue and Remind later are supported. Skipped completion can be reminded later; completed users should not repeatedly see the same flow.
- Duplicate three-step onboarding was fixed. Returning completed users skip onboarding. Every explicit sign-in checks notification availability and offers permission if needed. Ordinary resumes/tab switches should not restart onboarding.
- Sign-in UI follows the device theme and uses concise university-email instructions. The web uses the ClassMate logo with orbit/electron animation for sign-in and initial loading, replacing the generic loading skeleton.
- Android exchanges a Google ID token for a Supabase session. Web uses Google OAuth with PKCE and `/auth/callback`.

## 7. Push notifications and rollout readiness

- Supabase insertion/activation events create a shared outbox regardless of whether Android, desktop web or mobile web posts the notice.
- FCM sends are to eligible registered device tokens, not user-selectable public topics. Student batch membership and teacher-course assignment are rechecked immediately before sending.
- `/silent` suppresses new push events. Linked cancellation notice/event handling avoids duplicate alerts.
- **Durable per-event/per-device jobs**, unique identities, two-minute leases, claims of 100, **eight parallel sends** and **70-second invocation budget**.
- More chunks do not count as delivery failures. Temporary errors retry with exponential backoff/jitter and Retry-After; invalid tokens are removed; exhausted failures remain for explicit owner retry.
- Academic alerts precede release broadcasts. Scheduled/parallel workers use leases to avoid simultaneously claiming the same job. FCM itself cannot promise exactly-once delivery.
- Android persists deduplication per account/environment and reports receipt states; Web uses data-only FCM, one service-worker display path and persistent event deduplication.
- Device registration is platform-aware; signing out/disabling one browser must not remove Android tokens or every device's registration.
- Browser registrations carry Origin. Production permits current `classmatebd.vercel.app`; legacy/unknown old origins remain excluded until re-registration from the correct site. Migration 202610040010 fixed notifications attributed to the old web URL.
- Browser preference is cached per account independently of token success. Permission approval closes the onboarding prompt immediately; registration can continue/retry separately. Offline/registration failure must not reset the enabled preference to Off. Focus/online events retry without repeatedly prompting.
- Android preference reflects OS permission and channel blocking. Enable requests permission or opens settings; registration failure offers retry. It never makes Android permission optional.
- Release publisher queues an all-active-user version event. Android 1.1.15+ can open the updater from that alert; Android installation and Wi-Fi restrictions still apply.
- In-app notification permission, Android/browser permission, provider acceptance and actual device display are different stages. Do not claim delivery solely because FCM accepted a request.
- Owner-only System health includes queue size/age, acceptance/failures/receipt states, database size/largest tables and timestamped verified hosting/usage snapshots. Non-owner access denied server-side; no tokens/private contact data in diagnostics.
- Queue age >5 minutes and allowance use >80% are warnings. Unavailable/stale metrics are labelled explicitly.

### Updater

- GitHub metadata contains version code/name, APK URL/size/SHA-256, optional minimum-supported version, mandatory flag, date and notes.
- Verifier checks file size/hash, package and exact metadata version, newer-than-installed version, installed signing identity or valid signing lineage. **Never bypass certificate verification to make a debug app accept production updates.**
- Downloader streams into app-private storage and cleans partial files. Metadata requests use a cache-busting query. GitHub latest redirects can briefly be stale immediately after publication; verify both versioned and fresh latest metadata.
- WorkManager checks about every six hours, with foreground checks when enough time has elapsed; manual Profile Check for updates uses the same verifier. Automatic updates and Wi-Fi-only preferences remain supported.
- PackageInstaller handles installation; Android can require user confirmation and Install unknown apps permission. Do not promise entirely silent installation on every device.
- Current background worker shows generic **“ClassMate update rejected — The release could not be verified”** for multiple permanent errors. Exact cause is logged under `ClassMateUpdate`. The generic message alone is not proof of a bad signing key. No new persisted user-facing detailed diagnostics were implemented in this investigation.
- Phone profile conflict: APK identity is shared across Android users. Main-user uninstall does not remove a Guest copy. `dumpsys package` per-user installed flags revealed this. Do not delete a Guest app/user or its data without required authorization.

### Release procedure

1. Inspect pending source and preserve unrelated changes. Increment versionCode/name for a new release; do not overwrite/reuse immutable published identities casually.
2. Build/sign from current source with existing key0. User's path is **`release/app-release.apk`**. `app/release/app-release.apk` is an older July artifact and must not be substituted.
3. Validate with `scripts/publish-classmate-github-update.ps1 -ApkPath ./release/app-release.apk -ValidateOnly`.
4. Commit/push relevant source before publishing. The script checks its release-source paths and remote branch HEAD. Do not indiscriminately add credentials/private fixture reports/deliverables.
5. Publish with the same script, meaningful release notes and APK path. It creates a draft, uploads APK then metadata, checks sizes/digest/source commit, and publishes latest.
6. `scripts/notify-classmate-release.ps1` queues the version announcement with ignored server credentials. Enqueue is idempotent. Verify success separately from actual phone display.
7. If withdrawn, delete/unpublish release and cancel only its pending/leased/failed delivery jobs. Preserve existing receipts; leave unrelated notices/data untouched. Already-sent alerts cannot be recalled.

At handoff, versions 1.1.22/1.1.23 remain withdrawn. Do not silently republish them. Original mismatch was debug-versus-production installation, not a corrupted production keystore.
